# 系统设计：设计一个短视频推荐系统

> 搜推方向几乎必出；考的是能不能从日活一路算到每级的候选数、卡数和存储，再把实时性和降级讲清楚

## 一句话结论

按这个顺序走：**问清需求 → 从日活算 QPS → 定漏斗每级的候选数并算算力 → 算存储（索引、行为序列、embedding、已看过滤）→ 画架构 → 讲实时训练与参数同步 → 冷启动、多目标、降级**。以快手公开的量级为锚：日活 3.46 亿、人均每天 133.7 次播放、每天新发布 4500 万个视频；每次请求返回 8 个视频（假设），平均约 6.7 万 QPS，按 3 倍峰均比是 20 万（OneRec 报告的推荐 QPS 在 40 万以上，同一量级）。精排每请求 200 个候选时，峰值每秒给 4000 万个候选打分（TWIN 报告峰值每秒 3000 万个视频）。十亿级候选池用 IVF-PQ 每条 24 字节，一份索引 24 GB；用 HNSW 是 768 GB，要分片。行为序列每人 $10^4$ 条、每条 16 字节，共 55 TB；已看过滤用 1% 误判的布隆过滤器，每人 12 KB，共 4.2 TB。样本从曝光到进训练 8 分钟以内，参数每 5 分钟推到线上（TWIN 的做法）。

## 推导

### 第一步：把题目问清楚

1. **场景**：单列沉浸式（一次一个视频，下滑触发）还是双列（一次一屏，点击进入）？决定每次请求返回几个、主目标是完播 / 时长还是点击。
2. **规模**：日活、人均播放、候选池多大、每天新增多少。
3. **延迟**：服务端 P99 多少（本页按 120 ms 设计，假设）；能不能预取下一批。
4. **目标**：时长、完播、互动（点赞、评论、关注、分享）、创作者生态（新视频要有曝光）、商业化。
5. **新鲜度**：新视频多久能被推出去；用户刚看完的行为多久能影响下一次推荐。

### 第二步：容量估算

**流量**：

| 量 | 算式 | 结果 |
|---|---|---|
| 每天播放 | $3.46\times10^8 \times 133.7$ | $4.6\times10^{10}$（TWIN 报告每天 460 亿次播放） |
| 每天请求 | $4.6\times10^{10} / 8$（每请求 8 个，假设） | $5.8\times10^9$ |
| 平均 QPS | $5.8\times10^9 / 86400$ | $6.7\times10^4$ |
| 峰值 QPS | × 3（峰均比，假设） | $2\times10^5$ |

**漏斗和算力**（单候选 FLOPs 是假设，每卡有效 $1.1\times10^{13}$ FLOP/s 的来历见 [搜推全景](/recsys/funnel-overview)）：

| 级 | 每请求输入 → 输出 | 单候选 FLOPs | 峰值每秒打分数 | 算力 | 卡数 |
|---|---|---|---|---|---|
| 召回 | $10^9$ → $10^4$ | 用户塔 $10^7$ / 请求 + ANN | $2\times10^5$ 次检索 | 主要是检索 | CPU / GPU 检索集群 |
| 粗排 | $10^4$ → 200 | $10^5$ | $2\times10^9$ | $2\times10^{14}$ | 约 18 |
| 精排 | 200 → 50 | $2\times10^7$ | $4\times10^7$ | $8\times10^{14}$ | 约 73 |
| 重排 | 50 → 8 | 小 | | | CPU |

卡数只是算力下界；按 [排序服务](/recsys/ranking-serving) 的分析，时间大头在取特征和查 embedding，实际机器数由它们和冗余（跨机房、N+2）决定。

**存储**：

| 对象 | 算式 | 结果 |
|---|---|---|
| ANN 索引（IVF-PQ，$m = 16$ 字节码 + 8 字节 id） | $10^9 \times 24$ B | 24 GB / 份 |
| ANN 索引（HNSW，$d = 128$、$M = 32$） | $10^9 \times 768$ B | 768 GB，要分片 |
| 行为序列（每人 $10^4$ 条 × 16 B，假设） | $3.46\times10^8 \times 160$ KB | 55 TB |
| 视频 id embedding（$10^{10}$ 个 × 64 维 fp32，假设） | $10^{10} \times 256$ B | 2.56 TB |
| 已看过滤（每人 $10^4$ 个，1% 误判） | 见第五步 | 4.2 TB |
| 样本日志（每条 1 KB 特征快照，假设） | $4.6\times10^{10} \times 1$ KB / 天 | 46 TB / 天 |

**新视频入索引**：$4.5\times10^7 / 86400 \approx 520$ 个 / 秒，平均不大，但要分钟级可召回。

### 第三步：架构

```
App ── 网关 ── 推荐编排服务（mixer）
                 │
                 ├─ 用户画像 / 行为序列存储（KV，按 user_id 分片）
                 ├─ 已看过滤（布隆过滤器）
                 │
                 ├─ 召回（并行，每路有配额和超时）
                 │    ├ 双塔 + ANN（IVF-PQ / HNSW 分片）
                 │    ├ i2i：最近看过的视频的相似视频
                 │    ├ 关注作者的新作品
                 │    ├ 热门 / 地域
                 │    └ 新视频扶持池
                 ├─ 合并、去重、过滤 → 约 1 万个
                 ├─ 粗排（双塔内积或轻量 DNN）→ 200
                 ├─ 精排（多任务 + 长序列，GPU）← 特征服务、embedding 服务
                 └─ 重排（打散、多样性、业务规则）→ 8 个

曝光 / 播放日志 ─ 消息队列 ─ 流式拼样本 ─ 在线训练 ─ 参数同步（分钟级）─ 排序 / 召回服务
                                                └─ 物品塔 ─ 索引构建 ─ ANN 服务
```

### 第四步：召回与索引

1. **多路召回**，每路配额、超时就丢，合并后约 1 万个，见 [搜推全景](/recsys/funnel-overview)。
2. **双塔**：用户塔在线算，物品向量离线算；训练用 in-batch 负样本 + logQ 校正，见 [向量召回](/recsys/ann-retrieval)。
3. **索引选型**：十亿级候选池，单机放不下 HNSW 的 768 GB，选 IVF-PQ（每份 24 GB，可以每台机器一份完整副本，靠副本扛 QPS）加原始向量重排；或者 HNSW 按物品分 8 片、每片约 100 GB，查询扇出到所有分片再合并。前者省内存、扇出少，后者召回 / 延迟曲线更好。
4. **新鲜度**：新视频生成向量后增量插入（每秒约 520 个）；物品塔更新后全量重建索引，和用户塔同版本原子切换。

### 第五步：排序与特征

1. **精排模型**：多任务（完播、时长、点赞、关注、分享……），用户长期兴趣用 TWIN 式的两级长序列（GSU 从 $10^4$ 条挑 100 条，ESU 精算），见 [长序列](/recsys/long-sequence)。
2. **取特征**：用户侧一次、物品侧 200 次；物品特征本地缓存；线上用到的特征值落日志供训练拼样本，见 [排序服务](/recsys/ranking-serving)、[样本管线](/recsys/sample-pipeline)。
3. **多目标融合**：最终分常用各目标预估值的加权组合，权重靠 A/B 调。OneRec 报告指出快手有上百个目标，手工调融合权重既不准也难维护，它改用一个奖励模型学「好推荐」的分数。

**已看过滤**：每个用户看过的视频不能再推。布隆过滤器对 $n$ 个元素、误判率 $p$ 需要的位数：

$$
\frac{\text{bits}}{n} = \frac{-\ln p}{(\ln 2)^2},\qquad k = \frac{\text{bits}}{n}\ln 2
$$

$p = 1\%$：$4.605 / 0.4805 = 9.6$ 位 / 元素，哈希函数 $k = 6.6$，取 7 个。每人 $10^4$ 个视频约 12 KB，3.46 亿人约 4.2 TB，按 user_id 分片放内存。误判的代价是 1% 没看过的视频被误过滤，可以接受；反过来漏判（看过的又推）不会发生。

### 第六步：实时性：训练与参数同步

TWIN 报告的快手做法：每天 460 亿条播放和互动日志实时预处理，从发生到被用于训练不超过 8 分钟；训练系统通过消息队列每 5 分钟把最新参数同步到离线推理和线上服务；物品侧的预计算投影每 15 分钟刷新一次。

要讲清楚的点（细节见 [在线学习](/recsys/online-learning)）：

1. **样本拼接**：曝光和后到的行为（播完、点赞）按 request_id 拼；完播这类标签要等视频播完，要设等待窗口。
2. **增量同步**：只推这几分钟内变化过的 embedding 行和 dense 参数，不推全量。
3. **一致性**：召回的用户塔和物品索引必须同版本；排序的 embedding 服务和 dense 服务要同版本或兼容。
4. **回滚**：参数每 5 分钟一版，监控线上指标，异常时回到上一版。

### 第七步：冷启动

1. **新视频**：没有交互，id embedding 是随机的。用内容特征（多模态 embedding、标题、作者）进物品塔，或者用 semantic ID 让它和相似老视频共享 token，见 [生成式推荐](/recsys/generative-rec)；再用新视频扶持池给保底曝光，攒到一定曝光后回到正常竞争。
2. **新用户**：没有序列。用设备、地域、来源渠道和热门兜底，前几次请求加大探索；行为实时写进序列，下一次请求就能用上。

### 第八步：降级与高可用

按伤害从小到大（详见 [排序服务](/recsys/ranking-serving)）：特征超时用默认值 → 丢超时的召回路 → 精排候选 200 → 100 → 关长序列分支 → 换轻模型 → 返回预取 / 热门结果 → 限流。另外：

1. 多机房部署，每个机房 N+2 冗余；索引和模型版本跨机房一致。
2. 客户端一次多拿一些（预取），服务端短暂不可用时用户仍能刷几屏。

### 第九步：演进

级联的问题是每级只看到上一级留下的，且一半以上资源在通信和存储上。快手的 OneRec 用一个 encoder-decoder 直接生成视频的 semantic ID，承接了主场景约 25% 的 QPS，运营成本是级联的 10.6%（报告数据）。面试里可以把它作为「下一步」讲，见 [生成式推荐](/recsys/generative-rec)。

### 取舍汇总

| 决策 | 选项 A | 选项 B | 怎么选 |
|---|---|---|---|
| ANN 索引 | HNSW 分片：召回好、内存大、扇出 | IVF-PQ 整份副本：省内存、要重排 | 十亿级、内存受限选 B |
| 精排候选数 | 多：效果好、算力线性涨 | 少：省算力、好候选可能被截掉 | 看精排 top-$k$ 在粗排里的召回率曲线 |
| 参数同步频率 | 分钟级：跟上兴趣变化 | 小时 / 天级：稳、好回滚 | 短视频选分钟级，配好监控和回滚 |
| 物品侧预计算 | 缓存：省算力 | 实时算：最新 | 只和物品有关的部分缓存，几分钟刷新 |
| 已看过滤 | 布隆过滤器：省内存、有误判 | 精确集合：每人 80 KB（8 B × $10^4$） | 选布隆，1% 误判可接受 |

## 面试追问

::: details Q：QPS 怎么从日活算出来？
日活 × 人均播放 ÷ 每次请求返回的视频数 ÷ 86400 得平均 QPS，再乘峰均比。$3.46\times10^8 \times 133.7 / 8 / 86400 \approx 6.7\times10^4$，峰值按 3 倍约 $2\times10^5$。
:::

::: details Q：十亿级候选池的召回索引怎么放？
HNSW 每条约 768 B（$d = 128$、$M = 32$），十亿条 768 GB，只能分片、查询扇出再合并；IVF-PQ 每条 24 B，一份 24 GB，每台机器放一份完整副本，靠副本扛 QPS，用原始向量重排补精度。内存受限选 IVF-PQ。
:::

::: details Q：已看过滤用什么数据结构？要多少内存？
布隆过滤器。误判率 $p$ 时每元素 $-\ln p / (\ln 2)^2$ 位，$p = 1\%$ 约 9.6 位；每人 $10^4$ 个视频 12 KB，3.46 亿人 4.2 TB，按 user_id 分片放内存。误判只会少推一点没看过的，不会重复推。
:::

::: details Q：用户刚点赞了一个视频，多久能影响推荐？
两条路径：行为实时写进用户序列，下一次请求的特征就带上了（秒级）；模型参数要等样本进训练（快手是 8 分钟内）、参数同步（每 5 分钟）后才变。前者靠特征实时性，后者靠在线学习。
:::

::: details Q：新视频怎么冷启动？
内容特征（多模态向量、作者）进物品塔或生成 semantic ID，让它不依赖交互也能被召回；新视频扶持池保底曝光；生成向量后分钟级插入索引。攒到一定曝光后按正常竞争。
:::

::: details Q：如果让你只改一处来省机器，你改哪？
先看钱花在哪：通常是精排的取特征和 embedding 查询，而不是 dense 计算。所以优先做物品特征 / embedding 的本地缓存和 batch 内去重、用户侧计算只做一次、长序列的物品侧投影预计算；其次才是减精排候选数。
:::
