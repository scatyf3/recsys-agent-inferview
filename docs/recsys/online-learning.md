# 在线学习与模型更新：流式训练、增量 checkpoint、参数同步到线上、AUC/GAUC/NE 与 A/B、回滚

> 用户兴趣按分钟变，模型就得按分钟更新：只把这段时间被改过的行推到线上，dense 部分慢慢推；快照可以稀，但上线前的检查和回滚路径一定要有

## 一句话结论

搜推的数据分布一直在漂（concept drift），模型越新越好：Facebook 从每周训练改成每天训练，NE 降约 1%；Monolith 在 Criteo 上把参数同步间隔从 5 小时缩到 30 分钟，在线 AUC 从 79.66 涨到 79.80，而不做在线训练的模型只有 79.42 左右（作者自测）。在线训练就是在批训练的模型上继续消费实时样本流，再定期把参数推给线上。推全量不现实（模型几 TB），所以只推这段时间被碰过的行：Monolith 每分钟推一次，按 10 万个 ID、1024 维估约 400 MB；dense 参数变得慢，每天推一次。持久化快照可以很稀：Monolith 每天一次，1000 台 PS、每台每天 0.01% 的故障率，平均 10 天坏一台、丢掉千分之一用户一天的更新。评估看 AUC（排序）、GAUC（按用户算再按曝光加权）、NE（对数损失除以背景点击率的熵）和校准度；上线前用 A/B，CTR 2% 时要测出 1% 的相对提升，每组约 770 万次曝光。在线学习出问题扩散得快，所以每次推送前要过一道检查，出事时线上切回上一版、训练回到上一个好的快照并从 Kafka 的 offset 重放。

## 推导

### 0. 记号

| 符号 | 含义 | 例子取值 |
|---|---|---|
| $\Delta t$ | 参数同步间隔 | 1 分钟（稀疏）、1 天（dense） |
| $K$ | 一个间隔内被更新过的不同 ID 数 | $10^5$ |
| $d$ | embedding 维度 | 1024 |
| $s$ | 每个数的字节数 | 4 |
| $N_{\text{PS}}$ | PS 台数 | 1000 |
| $f$ | 每台 PS 每天的故障概率 | 0.01% |
| $\bar{p}$ | 背景点击率（训练集平均） | 2% |
| $\delta$ | A/B 要检测的绝对差 | $\bar{p} \times 1\% = 0.0002$ |
| $z_{\alpha/2}, z_\beta$ | 显著性和功效对应的正态分位数 | 1.96（双侧 5%）、0.84（功效 80%） |

MB = $10^6$、GB = $10^9$、TB = $10^{12}$ 字节。

### 1. 为什么要在线学习

1. **分布在漂**：新物料每分钟都在上，热点几小时就过去，用户兴趣也在变。一个模型训完就开始变旧。
2. **新鲜度的收益是实测的**：
   1. Facebook 广告：训一天的数据，在之后 6 天上测，NE 逐天变差；每周训改成每天训，NE 降约 1%（[He et al. 2014](https://quinonero.net/Publications/predicting-clicks-facebook.pdf) §3.2，作者自测）。
   2. [Monolith](https://arxiv.org/abs/2209.07663)：Criteo 7 天数据，前 5 天批训练，后 2 天模拟在线训练（表 2，DeepFM，作者自测）：

| 同步间隔 | 在线训练的平均 AUC | 只批训练的平均 AUC |
|---|---|---|
| 5 小时 | 79.66 | 79.42 |
| 1 小时 | 79.78 | 79.44 |
| 30 分钟 | 79.80 | 79.43 |

3. **新 ID 要尽快有向量**：新物料没有 embedding 就只能用默认值，越早学到越早能被正确分发。

**两段式训练**（Monolith §2.2）：

1. **批训练**：改了模型结构，就在历史数据上从头训一遍，每条样本只过一遍（推荐数据量大、分布在变，多个 epoch 意义不大）。
2. **在线训练**：模型上线后训练不停，worker 直接从 Kafka 读实时样本（[样本与特征管线](/recsys/sample-pipeline)），更新训练侧 PS，再定期同步到服务侧 PS。

### 2. 参数同步：只推变了的

**为什么不推全量**（Monolith §2.2.3）：

1. 模型通常几 TB，整份替换要很久，期间服务不能停。
2. 服务侧要先收下新的一份再换掉旧的，内存要两倍，网络也扛不住。

**三条观察**决定了怎么推：

1. 模型大小几乎全在稀疏参数上。
2. 一小段时间里只有一小部分 ID 被训练到。
3. dense 参数变得比稀疏参数慢得多：动量类优化器里 dense 的动量在海量样本上累积，一个 batch 改不动多少；而一个稀疏行只在它的 ID 出现时才更新。

**做法**：

1. 训练侧维护一个 touched keys 集合：上次同步以来被更新过的 ID。
2. 每分钟把这些行推到服务侧 PS，服务侧逐行原地覆盖，不需要两倍内存，也不用停服。
3. dense 参数每天推一次，挑流量最低的时候（比如半夜）。这样线上的 dense 比 sparse 旧，但因为第 3 条观察，没看到明显损失（作者自测）。

**每次推多少**：

$$
V_{\text{sync}} = K \cdot d \cdot s
$$

Monolith 的例子：每分钟 $10^5$ 个 ID 被更新、$d = 1024$，$10^5 \times 1024 \times 4 = 410$ MB/分钟。假设全模型 5 TB，增量是全量的 1/12000。

**服务侧的细节**：

1. 训练侧淘汰的 ID 要同步成删除，否则服务侧的表只涨不缩（[Embedding 表的账](/recsys/embedding-tables)）。
2. 推之前可以顺手压缩：服务侧不需要优化器状态，权重可以存 fp16 或按行量化成 int8。
3. 一个请求可能读到一半新、一半旧的行；行内要原子（整行替换），行间的不一致可以容忍。

### 3. 增量 checkpoint 与快照频率

**两种东西**：

1. **全量快照**：每台 PS 把自己的分片完整写到持久存储。用来恢复挂掉的 PS、回滚、重新开始批训练。
2. **增量**：两次全量之间被改过的行（就是上面推给线上的那份）。全量 + 之后所有增量 = 任意时刻的模型，恢复时先加载全量再按顺序回放增量。

**快照多久一次**。快照越勤，挂了丢得越少，但几 TB 的内存拷贝和磁盘写入不便宜。Monolith 把快照间隔放宽到一天，几乎没看到效果损失（§3.2.2），算了一笔账：

1. 1000 台 PS，每台每天故障概率 0.01%：平均每天坏 $1000 \times 10^{-4} = 0.1$ 台，即每 10 天坏一台。
2. 坏一台就丢掉它上面一天的更新。日活 1500 万、用户 ID 均匀分到 1000 台 PS 上，丢的是 1.5 万个用户一天的反馈，每 10 天一次。
3. 对用户相关的稀疏特征，相当于 0.01% 的日活丢了一天；dense 参数变得慢，1000 台里丢一台一天的更新可以忽略。

这和 LLM 训练的容错很不一样：同步训练里一张卡挂了整个作业停，要靠高频 checkpoint 和快速重启（[大规模训练的容错](https://scatyf3.github.io/ai-infra-inferview/train/fault-tolerance)）；PS 架构下一台 server 挂了只影响它那一段参数，其他照常训练和服务。

### 4. 离线指标

**AUC**：随机取一个正样本和一个负样本，正样本分数更高的概率。只看排序，不看绝对值。

例：正样本分数 $\{0.9, 0.4\}$，负样本 $\{0.8, 0.3, 0.2\}$，共 $2 \times 3 = 6$ 对。0.9 赢 3 对，0.4 赢 0.3 和 0.2 两对，AUC $= 5/6 = 0.833$。

**GAUC**（[DIN，arXiv 1706.06978](https://arxiv.org/abs/1706.06978) 式 (10)）：先按用户分别算 AUC，再按曝光数加权平均：

$$
\text{GAUC} = \frac{\sum_{i} \text{imp}_i \cdot \text{AUC}_i}{\sum_i \text{imp}_i}
$$

$\text{imp}_i$ 是用户 $i$ 的曝光数。只有正样本或只有负样本的用户 AUC 没有定义，不参与计算。

为什么要它：线上排序是在同一个用户的候选之间比，全局 AUC 却把不同用户的样本混在一起比。例：用户 a 的样本（标签, 分数）是 $(1, 0.2), (0, 0.3), (0, 0.1)$，用户 b 是 $(1, 0.9), (1, 0.7), (0, 0.8)$。

1. 用户内：a 的 AUC 是 $1/2$（0.2 赢了 0.1、输给 0.3），b 也是 $1/2$（0.9 赢 0.8、0.7 输 0.8），GAUC = 0.5。
2. 全局：3 个正样本对 3 个负样本 9 对，赢 6 对，AUC = 0.667。

模型只学到了「用户 b 爱点」，没学会在同一个用户的候选里排序，全局 AUC 把这一点藏住了。

**NE**（He et al. 式 (1)）：平均对数损失除以「每条都预测背景点击率 $\bar{p}$」时的对数损失：

$$
\text{NE} = \frac{-\frac{1}{N}\sum_i \left[ y_i \log p_i + (1 - y_i)\log(1 - p_i) \right]}{-\left[\bar{p}\log\bar{p} + (1 - \bar{p})\log(1 - \bar{p})\right]}
$$

越低越好，1 表示和只会猜平均值一样。除以分母是因为点击率越接近 0，对数损失天然越小，不归一化就没法在不同点击率的场景之间比。

例：$\bar{p} = 2\%$，分母 $= 0.02 \times 3.912 + 0.98 \times 0.0202 = 0.0980$ nats；模型的平均 log loss 是 0.090，NE $= 0.090 / 0.0980 = 0.918$。

NE 同时受排序能力和校准影响；AUC 只受排序影响。所以再看一个**校准度**：$\sum_i p_i / \sum_i y_i$，应该接近 1。负采样后忘了校正（[样本与特征管线](/recsys/sample-pipeline)），AUC 不变，NE 和校准度会马上变差。

### 5. A/B 实验

离线指标涨了不代表线上涨，最后要看线上实验：流量随机分成对照组和实验组，比点击率、时长、收入等。

**要多少流量**。检测点击率的绝对差 $\delta$，每组需要的样本数（两样本比例检验的近似）：

$$
n \approx \frac{2\,(z_{\alpha/2} + z_\beta)^2\, \bar{p}(1 - \bar{p})}{\delta^2}
$$

$\bar{p} = 2\%$，想测出 1% 的相对提升（$\delta = 0.0002$），双侧 5% 显著性、80% 功效：

$$
n = \frac{2 \times (1.96 + 0.84)^2 \times 0.02 \times 0.98}{0.0002^2} = \frac{2 \times 7.84 \times 0.0196}{4\times10^{-8}} = 7.7\times10^6
$$

每组约 770 万次曝光。这里把每次曝光当独立的；实际按用户分流，同一个用户的曝光相关，方差更大，要按用户聚合算方差（或用 delta 方法），需要的量更多。

**在线学习下的 A/B 的坑**：两组模型都在用自己组的流量在线训练，实验组如果改变了推荐结果，它收到的样本分布也变了（反馈回路）；实验跑得越久，两个模型差得越多，结果混着「模型更好」和「数据不同」两种效应。

### 6. 推送前的检查与回滚

在线学习的风险：上游一个特征坏了、标签管线延迟了一小时（突然全是负样本），模型几分钟内就学歪，而且自动推上线。

**推送前检查**（每次同步前跑一遍）：

1. **样本**：这一段的正样本率、各特征的覆盖率和均值，和过去同一时段比，超出阈值就暂停训练。
2. **模型**：在最近一小段保留数据上算 AUC、NE、校准度，和上一版比；预测均值、NaN / Inf、参数范数有没有突变。
3. **灰度**：先推给一小部分流量，看线上指标，没问题再全量。

**回滚**：

1. 服务侧切回上一个好版本（保留最近几个全量快照加增量，就能回到任意一个检查点）。
2. 训练侧回到出问题之前的快照，修好数据后从 Kafka 对应的 offset 重放，补上中间的数据。Kafka 的保留时间要覆盖「发现问题 + 修复」的时间。

## 面试追问

::: details Q：在线学习为什么只同步变了的 embedding 行？dense 怎么办？
模型几 TB，全量替换要两倍内存、占满网络，期间还不能停服。一分钟里被训练到的 ID 只是一小部分：Monolith 按每分钟 10 万个 ID、1024 维估约 410 MB。dense 参数在海量样本上变得慢，每天推一次即可，Monolith 没观察到明显损失（作者自测）。
:::

::: details Q：同步间隔越短越好吗？代价是什么？
效果上越短越好：Monolith 在 Criteo 上 5 小时、1 小时、30 分钟的在线 AUC 是 79.66、79.78、79.80。代价是推送频率越高，网络和服务侧写入压力越大，坏模型推上去的速度也越快，检查要更快更自动。
:::

::: details Q：PS 的快照为什么可以一天一次？
算一笔：1000 台 PS、每台每天 0.01% 故障率，每 10 天坏一台，丢的是千分之一用户一天的更新，dense 部分几乎不受影响。PS 架构下一台挂了只影响它那一段参数，不像同步训练里一张卡挂了整个作业停。
:::

::: details Q：AUC、GAUC、NE 各看什么？
AUC 看全局排序能力；GAUC 先在每个用户内部算 AUC 再按曝光加权，更接近线上「同一个用户的候选怎么排」；NE 是归一化的对数损失，同时反映排序和校准。另外看校准度（预测之和 / 实际点击之和），负采样没校正时 AUC 不变，NE 和校准度会变差。
:::

::: details Q：离线 AUC 涨了，线上 A/B 没涨，可能是什么原因？
一是训练-服务不一致：离线用的特征和线上不同，或者离线有时间穿越；二是评估集和线上流量分布不同（比如离线只评已曝光的样本，线上候选更多）；三是全局 AUC 的提升来自用户间的区分，GAUC 没涨；四是 A/B 流量不够、方差太大，CTR 2% 时测 1% 的相对提升每组就要约 770 万次曝光。
:::

::: details Q：在线训练把模型训坏了，怎么发现、怎么恢复？
发现：每次推送前检查样本（正样本率、特征覆盖率）和模型（保留集上的 AUC / NE / 校准度、预测均值、NaN），线上灰度再看实时指标。恢复：服务切回上一个好版本；训练回到出问题前的快照，修好数据后从 Kafka 的 offset 重放。
:::

## 手撕

AUC（按秩和算，处理并列）、GAUC、NE：

```python
import numpy as np
from collections import defaultdict

def auc(y, s):
    """正样本排在负样本前面的概率（并列算一半），O(n log n)"""
    y, s = np.asarray(y), np.asarray(s)
    order = np.argsort(s, kind="mergesort")
    ranks = np.empty(len(s)); ranks[order] = np.arange(1, len(s) + 1)
    for v in np.unique(s):                       # 并列的分数取平均名次
        m = s == v
        ranks[m] = ranks[m].mean()
    n_pos, n_neg = y.sum(), len(y) - y.sum()
    return (ranks[y == 1].sum() - n_pos * (n_pos + 1) / 2) / (n_pos * n_neg)

def gauc(user, y, s):
    """按用户算 AUC，再按曝光数加权；全正或全负的用户 AUC 无定义，跳过"""
    groups = defaultdict(list)
    for u, yi, si in zip(user, y, s):
        groups[u].append((yi, si))
    num = den = 0.0
    for rows in groups.values():
        yy, ss = zip(*rows)
        if 0 < sum(yy) < len(yy):
            num += len(rows) * auc(yy, ss)
            den += len(rows)
    return num / den

def ne(y, p):
    """归一化交叉熵：平均 log loss / 用平均点击率当预测时的 log loss"""
    y, p = np.asarray(y), np.clip(np.asarray(p), 1e-7, 1 - 1e-7)
    ll = -np.mean(y * np.log(p) + (1 - y) * np.log(1 - p))
    ctr = y.mean()
    return ll / -(ctr * np.log(ctr) + (1 - ctr) * np.log(1 - ctr))

y = [1, 1, 0, 0, 0]; s = [0.9, 0.4, 0.8, 0.3, 0.2]
print("AUC", round(auc(y, s), 4))                               # 5 / 6
user = ["a"] * 3 + ["b"] * 3
y2 = [1, 0, 0, 1, 1, 0]; s2 = [0.2, 0.3, 0.1, 0.9, 0.7, 0.8]  # b 的分数整体更高，但各自用户内排得一般
print("全局 AUC", round(auc(y2, s2), 4), " GAUC", round(gauc(user, y2, s2), 4))
rng = np.random.default_rng(0)
p_true = rng.uniform(0.005, 0.05, 100_000); yy = rng.random(100_000) < p_true
print("NE 真实概率", round(ne(yy, p_true), 3), " NE 常数", round(ne(yy, np.full(100_000, yy.mean())), 3))
# AUC 0.8333
# 全局 AUC 0.6667  GAUC 0.5
# NE 真实概率 0.976  NE 常数 1.0
```

最后一行值得注意：即使模型输出的就是每条样本的真实概率，NE 也只有 0.976，因为这批样本的点击率本身只在 0.5% 到 5% 之间变化，能解释的不确定性就这么多。NE 的绝对值要和同一个场景的基线比，不能跨场景比。常见变体：加权 AUC（按样本权重）、流式算 AUC（按分数分桶计数）、算校准度 $\sum p / \sum y$。
