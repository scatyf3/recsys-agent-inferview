# 搜推系统全景：召回、粗排、精排、重排

> 漏斗的每一级都是同一笔账：这一级的输入候选数 × 单候选成本 × 峰值 QPS，要落在这一级的延迟预算和机器预算里

## 一句话结论

搜推系统用多级漏斗把候选从千万、十亿级缩到十几个：召回（亿级 → 上万）、粗排（上万 → 几百）、精排（几百 → 几十）、重排（几十 → 一屏）。阿里 COLD 给的典型规模是「千万 → 上万 → 几百 → 几十」，粗排和精排各自的延迟上限约 10–20 ms；YouTube 是「百万 → 几百 → 几十」，打分要在几十毫秒内完成。漏斗存在的原因是算力：本页的假设下，精排模型每个候选 $2\times10^7$ FLOPs，打满 $10^8$ 个候选每请求要 $2\times10^{15}$ FLOPs，只打 500 个是 $10^{10}$，差 20 万倍。设计时按「每级总成本 $N_{i-1} c_i$ 大致相当、越贵的模型看越少的候选」来定截断数；延迟预算按串行的级相加，并行的召回分支取最慢的一路；扇出到多个分片时尾延迟会放大，每个分片 1% 慢、扇出 100 个，就有 63% 的请求被拖慢。搜索和推荐的漏斗形状一样，差别在搜索有 query：召回要加倒排、相关性是硬约束、热门 query 的结果可以缓存。

## 推导

### 0. 记号

| 符号 | 含义 | 例子取值 |
|---|---|---|
| $N_0$ | 候选池大小（可推荐的物品数） | $10^8$（假设） |
| $N_i$ | 第 $i$ 级输出的候选数（$i$ = 1 召回、2 粗排、3 精排、4 重排） | $10^4$、500、50、10（假设） |
| $c_i$ | 第 $i$ 级给一个候选打分的 FLOPs | 粗排 $10^5$、精排 $2\times10^7$（假设） |
| $Q$ | 峰值请求数，次 / 秒 | $10^5$（假设） |
| $t_i$ | 第 $i$ 级的延迟，ms | 见第 3 节 |
| $T$ | 服务端 P99 延迟预算，ms | 120（假设） |
| $F_{\text{eff}}$ | 一张推理卡的有效算力，FLOP/s | $1.1\times10^{13}$（假设，见第 2 节） |
| $p$ | 单个分片「慢」的概率 | 1% |
| $k$ | 一个请求扇出的分片数 | 100 |

1 GFLOP = $10^9$ FLOPs，1 PFLOP = $10^{15}$ FLOPs。

### 1. 漏斗长什么样

| 级 | 输入 → 输出 | 典型模型 | 延迟量级 | 出处 |
|---|---|---|---|---|
| 召回 | 千万～十亿 → 上万 | 多路：双塔 + ANN、i2i、热门、关注 | 十毫秒 | COLD 图 1、Instagram |
| 粗排 | 上万 → 几百 | 双塔内积或轻量 DNN | 10–20 ms | COLD §1、§3 |
| 精排 | 几百 → 几十 | 多任务大模型 + 长序列 | 10–30 ms | DIN、SIM |
| 重排 | 几十 → 一屏 | 多样性、打散、业务规则 | 几毫秒 | |

几个公开的口径：

1. 阿里 COLD（广告）：图 1 标的是「tens of millions → tens of thousands → hundreds → tens」；粗排的输入「often reaches ten thousand」，粗排和精排都有 10–20 ms 的延迟上限。
2. YouTube DNN：候选生成从百万级视频里出几百个，排序再出几十个，打分要在几十毫秒内完成。
3. Instagram Explore：召回从十亿级里选出候选，第一阶段轻量排序处理几千个，第二阶段重模型只看前 100 个。

**为什么要分级**。算一笔（本页假设的数）：

$$
\text{每请求算力} = \sum_i N_{i-1}\, c_i
$$

1. 精排如果直接打 $N_0 = 10^8$ 个：$10^8 \times 2\times10^7 = 2\times10^{15}$ FLOPs / 请求。
2. 分级后：粗排 $10^4 \times 10^5 = 10^9$，精排 $500 \times 2\times10^7 = 10^{10}$，召回和重排各约 $10^8$（假设），合计约 $1.1\times10^{10}$。
3. 差 $2\times10^{15} / 1.1\times10^{10} \approx 1.8\times10^5$ 倍。

分级的代价是**前一级筛掉的，后一级永远看不到**：粗排漏掉的好候选，精排再准也救不回来。所以截断数 $N_i$ 不是越小越好，常用离线的「精排 top-$k$ 有多少落在粗排 top-$N_2$ 里」这类召回率曲线，和算力一起定。Instagram 的第一阶段排序直接用「是否进入第二阶段 top-$K$」当标签训练，就是让粗排去学精排的排序。

**设计规则**：每一级的总成本 $N_{i-1} c_i$ 大致在同一量级（上面是 $10^8$、$10^9$、$10^{10}$），单候选越贵的模型看的候选越少。某一级的总成本远超其他级，就该在它前面再加一级，或者把它的输入截得更狠。

### 2. QPS 和算力：按峰值 × 候选数来备

一级排序每秒要打的分数是 $Q \times N_{i-1}$，算力需求是：

$$
\text{FLOP/s}_i = Q \cdot N_{i-1} \cdot c_i,\qquad \text{卡数}_i = \frac{Q \cdot N_{i-1} \cdot c_i}{F_{\text{eff}}}
$$

算一笔：

1. 精排：$Q = 10^5$，$N_2 = 500$，每秒打 $5\times10^7$ 个候选。快手 TWIN 报告排序系统峰值每秒 3000 万个视频，是同一量级。
2. 算力：$5\times10^7 \times 2\times10^7 = 10^{15}$ FLOP/s。
3. 有效算力：假设一张推理卡 fp16 峰值约 100 TFLOP/s。快手 OneRec 报告里，原来的排序模型推理 MFU 只有 11.2%，取 $F_{\text{eff}} \approx 1.1\times10^{13}$ FLOP/s。
4. 卡数：$10^{15} / 1.1\times10^{13} \approx 90$ 张。精排直接打 $10^8$ 个候选的话，是它的 20 万倍，约 1800 万张。

MFU 低是常态：OneRec 报告级联架构里超过 50% 的服务资源花在通信和存储上，而不是计算。所以「需要几张卡」常常由取特征、查 embedding 的网络开销决定，见 [排序服务](/recsys/ranking-serving)。

**峰值和平均**：机器按峰值备。日志里算出的是平均 QPS，乘上峰均比（短视频晚高峰常见 2–3 倍，假设）才是 $Q$。

### 3. 延迟预算怎么分

漏斗里的级是**串行**的：上一级出结果，下一级才能开始。一级内部的多路召回是**并行**的：

$$
T \ge t_{\text{接入}} + \max_j t_{\text{召回},j} + t_{\text{合并}} + t_{\text{粗排}} + t_{\text{精排}} + t_{\text{重排}}
$$

一个服务端 P99 预算 120 ms 的分法（假设）：

| 环节 | 预算 | 说明 |
|---|---|---|
| 接入、取用户画像和行为序列 | 15 ms | 一次 KV 批量读 |
| 召回 | 20 ms | 6 路并行，取最慢一路 |
| 合并、去重、已看过滤 | 5 ms | |
| 粗排 | 15 ms | 上万个候选，含取物品特征 |
| 精排 | 40 ms | 取特征约 10 ms + 推理约 30 ms |
| 重排 | 5 ms | |
| 余量 | 20 ms | 网络抖动、GC、重试 |

对照公开数字：SIM 说排序服务延迟一般要小于 30 ms；DIN 要在 10 ms 内给几百个广告打分；DeepRecSys 汇总的 SLA 从 5 ms（NCF）到几百毫秒（Facebook 的 DLRM 类模型）不等，差别来自业务。

**并行召回取 max，所以最慢的那一路决定召回耗时**。一路召回超时时，做法是不等它，直接用已返回的结果，见 [排序服务的降级](/recsys/ranking-serving)。

### 4. 扇出放大尾延迟

一个请求要等所有分片返回（召回的 ANN 分片、特征存储的分片），只要有一个分片慢，整个请求就慢：

$$
P(\text{请求慢}) = 1 - (1 - p)^k
$$

算一笔（[The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) 里的例子）：每个分片 1% 的请求超过 1 s，$p = 0.01$，扇出 $k = 100$：$1 - 0.99^{100} = 63.4\%$ 的请求会超过 1 s。分片的 P99 变成了整个请求的中位数。

对策：

1. 减少扇出：特征按用户 id 路由到同一个分片，一次批量读拿完。
2. 对冲请求（hedged request）：一个分片超过它的 P95 还没回，就向它的副本再发一次，谁先回用谁。
3. 允许部分结果：召回的某个分片或某一路超时就丢掉，不等。

### 5. 搜索和推荐在系统上的差别

| | 推荐（信息流） | 搜索 |
|---|---|---|
| 请求的输入 | 用户、上下文，没有 query | 有 query |
| 召回 | 双塔 + ANN、i2i、热门等多路 | 再加倒排索引（BM25 等词匹配）和 query 向量检索 |
| 排序目标 | 互动（点击、时长、点赞……） | 相关性是硬约束，再叠互动 |
| 结果缓存 | 每个用户不同，基本不能缓存结果 | 热门 query 重复多，结果可以缓存 |
| 标签 | 几乎全靠行为日志 | 还有人工相关性标注（Pinterest 用 5 档） |
| 延迟体感 | 可以预取下一屏 | 用户在等，交互式 |

1. 搜索的召回多了一条词匹配通道：倒排表按词组织，query 的每个词拉出一个 posting list 再求并 / 交，这条通道对精确的名字、型号最准，向量检索补语义相近的。
2. 相关性要单独建模：Pinterest 的排序把相关性模型的分数和互动预估一起用来决定最终顺序，否则排序会被「容易点但不相关」的内容带偏，见 [LLM 用于搜推](/recsys/llm-for-search)。
3. 推荐的一次请求通常返回一组（OneRec 里一个 session 是 5–10 个视频），请求由用户刷新或下滑触发，所以 QPS 和人均观看数直接挂钩，见 [系统设计](/recsys/system-design)。

### 6. 级联之外：生成式

快手 OneRec 用一个 encoder-decoder 生成模型替代召回、粗排、精排的级联，报告的运营成本是原级联系统的 10.6%，训练 / 推理 MFU 从 4.6% / 11.2% 提到 23.7% / 28.8%，在主场景承接约 25% 的 QPS。原因见 [生成式推荐](/recsys/generative-rec)。级联仍是今天的主流，面试默认讲级联。

## 面试追问

::: details Q：为什么不能用一个最好的模型直接给所有物品打分？
算力。本页假设下精排每个候选 $2\times10^7$ FLOPs，打 $10^8$ 个候选是每请求 $2\times10^{15}$ FLOPs，$10^5$ QPS 下要约 1800 万张卡。分级后每请求约 $1.1\times10^{10}$ FLOPs。代价是前一级漏掉的候选后面救不回来，所以截断数要按召回率曲线和算力一起定。
:::

::: details Q：每一级的截断数怎么定？
两头约束：算力上，$Q \cdot N_{i-1} \cdot c_i$ 不能超过这一级的机器预算，$N_{i-1} c_i$ 也不能超过延迟预算能算完的量；效果上，离线看「精排的 top-$k$ 有多少落在粗排的 top-$N_2$ 里」，曲线平了就不必再加。最后用 A/B 确认。
:::

::: details Q：粗排和精排排序不一致怎么办？
粗排模型更小，排序和精排有差距，好候选会在粗排被截掉。常见做法是让粗排学精排：用「这个候选在精排里是否进 top-$K$」当标签（Instagram 的第一阶段排序就是这么训的），或者直接蒸馏精排的分数。
:::

::: details Q：多路召回的结果怎么合并？
每路给配额，按配额截断后合并去重，再过滤已看、黑名单。配额由各路的离线召回率和线上效果定；某一路超时就丢掉，不阻塞其他路。合并后的总数就是粗排的输入 $N_1$。
:::

::: details Q：一个请求要查 100 个分片，为什么 P99 会变差？
请求要等最慢的分片。每个分片慢的概率 $p$，扇出 $k$ 个，请求慢的概率是 $1 - (1-p)^k$；$p = 1\%$、$k = 100$ 时是 63%。对策是减少扇出、对冲请求、允许部分结果。
:::

::: details Q：搜索和推荐的系统，最大的不同在哪？
搜索有 query：召回要有倒排索引这条词匹配通道，相关性是排序的硬约束、要有人工标注和专门的相关性模型，热门 query 的结果可以缓存。推荐没有 query，结果因人而异基本不能缓存，标签几乎全来自行为日志。
:::
